💡 Tip de estudio: no leas pasivamente. Cada vez que veas un bloque de código, cópialo y pruébalo en tu máquina. Este curso se aprende haciendo.

El hilo conductor: una metáfora

OpenClaw es como una central de mensajería (Gateway) conectada a una oficina de asistentes (agentes).
El Gateway es el edificio: recibe cartas (mensajes) de todos los canales y las reparte.
Cada agente es un empleado con su propio escritorio (workspace) y su propio archivador (memoria).
Las tools/skills son las herramientas de cada cajón.
El cron es el encargado que pone alarmas y hace tareas a horas fijas.
El MCP es el teléfono para pedir favores a servicios externos.
La memoria vectorial (RAG) es el archivo inteligente que encuentra papeles por significado.
Docker es el contenedor donde metes toda la oficina para mudarla a cualquier máquina.

Glosario rápido

TérminoQué es (en una línea)
GatewayEl proceso central que conecta canales, agentes y herramientas.
WorkspaceLa carpeta "hogar" del agente, donde vive y crea archivos.
SesiónUna conversación/contexto entre un usuario y un agente.
ToolUna capacidad que el agente puede invocar.
SkillUn paquete de instrucciones (con SKILL.md) que le enseña algo al agente.
CronEl programador de tareas automáticas del gateway.
MCPModel Context Protocol: estándar para conectar herramientas/servicios externos.
EmbeddingVector numérico que representa el significado de un texto.
RAGRecuperación aumentada: dar contexto relevante al modelo desde una base.
DockerContenedores para empaquetar y desplegar aplicaciones reproducibles.

Módulo 1: Fundamentos avanzados del gateway y la arquitectura

Duración: 1.5 h · Objetivo: explicar la arquitectura de OpenClaw y diagnosticar el gateway como operador.

Objetivos de aprendizaje

  • Explicar cómo encajan Gateway, agente, workspace, sesiones y canales.
  • Leer y modificar ~/.openclaw/openclaw.json con seguridad.
  • Configurar cadenas de fallback de modelos.
  • Diagnosticar el gateway (status, doctor, logs).
  • Aplicar medidas básicas de seguridad.

1.1 Arquitectura: el edificio y sus empleados

 ┌─────────────────────────────────────────────┐
 │ GATEWAY │
 │ (el edificio / proceso central) │
 │                                              │
 │ Canales → Telegram, Discord, Slack,          │
 │ WhatsApp, WebChat, Signal…                  │
 │        │                                    │
 │        ▼                                    │
 │ Agentes → [agente A] [agente B] [agente C]  │
 │               │        │        │           │
 │          workspace  workspace  workspace    │
 │          (escritorio propio)                 │
 └─────────────────────────────────────────────┘

Piezas clave:

  • Gateway: el proceso que corre todo. Es la única fuente de verdad para sesiones, rutas y conexiones. Si no corre, nada funciona.
  • Agente (agent runtime): el "empleado" que usa modelos de IA y herramientas.
  • Workspace: la carpeta privada de cada agente (~/.openclaw/workspace). Su escritorio y su memoria. No es un sandbox duro.
  • Sesión: una conversación con contexto.
  • Canal: la vía de entrada/salida (Telegram, Discord, etc.).
💡 Analogía: el Gateway es el interruptor general de luz. Si lo apagas, toda la oficina se queda a oscuras.

¿Dónde está cada cosa?

QuéDónde vive
Configuración~/.openclaw/openclaw.json
Workspace (hogar del agente)~/.openclaw/workspace
Credenciales (API keys, OAuth)~/.openclaw/credentials/ y perfiles de auth
Sesiones (transcripciones)~/.openclaw/agents/<agentId>/sessions/
Config por agente~/.openclaw/agents/<agentId>/agent/
⚠️ No guardes secretos en el workspace. API keys y tokens van en ~/.openclaw/ (o variables de entorno), nunca en archivos del workspace ni en git.

1.2 Configuración profunda: openclaw.json

{
  // Agentes
  agents: {
    defaults: {
      workspace: "~/.openclaw/workspace",
      // sandbox: { enabled: true, ... }, // aislamiento opcional
    },
    list: [
      { id: "soporte", workspace: "~/.openclaw/workspace-soporte" }
    ],
  },

  // Canales
  channels: {
    telegram: { /* token, allowFrom, ... */ },
    whatsapp: { allowFrom: ["+15555550123"] },
  },

  // Mensajes y grupos
  messages: {
    groupChat: { mentionPatterns: ["@openclaw"] },
  },
}

Puntos clave:

  • agents.defaults.workspace fija el escritorio por defecto.
  • agents.list[] define agentes extra, cada uno con su workspace.
  • channels.*.allowFrom restringe quién puede escribir (allowlist).
  • El sandboxing (agents.defaults.sandbox) aísla las operaciones del agente.
💡 Analogía: openclaw.json es el organigrama y reglamento de la oficina: quién trabaja dónde y quién tiene llaves de qué puertas.

1.3 Modelos y fallbacks: no te quedes a oscuras

Un fallback es un plan B: si el modelo principal falla, el agente prueba el siguiente.

{
  agents: {
    defaults: {
      model: "anthropic/claude-sonnet-4-5",
      fallbacks: [
        "openai/gpt-4o",
        "openrouter/meta-llama/llama-3.3-70b-instruct:free",
      ],
    },
  },
}

Override por sesión: cambia el modelo de una sesión desde el chat (slash command /model) sin tocar el default global.

💡 Tip: elige fallbacks de proveedores diferentes para que una caída de un proveedor no tire todo el stack.

1.4 Diagnóstico: ser el técnico de la oficina

openclaw status            # estado general del gateway
openclaw gateway status   # estado específico del gateway
openclaw doctor           # diagnóstico profundo + arreglos
openclaw logs --follow    # ver logs en vivo

La "escalera" de resolución de problemas:

openclaw status
openclaw gateway status
openclaw cron status      # si el problema es de tareas programadas
openclaw logs --follow    # mira el error real
openclaw doctor           # deja que diagnostique y proponga arreglos
💡 Analogía: estos comandos son el fontanero, el electricista y el inspector de tu edificio.

1.5 Seguridad básica: las llaves de la oficina

  • Tokens y API keys: van en ~/.openclaw/ o variables de entorno, nunca en git ni en el workspace.
  • Allowlists: channels.<canal>.allowFrom limita quién puede escribirte.
  • Permisos de herramientas: la policy de tools.exec controla qué comandos puede correr el agente.
  • Sandboxing: agents.defaults.sandbox aísla las operaciones del agente.
⚠️ Regla de oro: menos privilegios, siempre. Dale al agente solo lo que necesita para su tarea.

Errores comunes

  1. "No responde nada": el Gateway está caído. openclaw status → openclaw gateway restart.
  2. Confundir workspace con config: editar openclaw.json cuando querías editar el workspace (o viceversa).
  3. Guardar secrets en el workspace: nunca.
  4. Sin fallbacks: un solo modelo = punto único de fallo.

Ejercicios

  • ☐ Ejecuta openclaw status y openclaw doctor. Resuelve al menos un warning.
  • ☐ Abre ~/.openclaw/openclaw.json y localiza: agents, channels, tools.
  • ☐ Configura una cadena de fallbacks de 2 modelos distintos.
  • ☐ Identifica qué canales están conectados y qué allowlists tienen.

Resumen

  • El Gateway es el proceso central; sin él, nada corre.
  • El workspace es el hogar privado del agente.
  • openclaw.json es el organigrama.
  • Fallbacks de modelo = resiliencia.
  • Diagnóstico: status → logs → doctor.
  • Seguridad: menos privilegios, allowlists, sin secrets en el workspace.

Módulo 2: Creación de funciones (tools) personalizadas

Duración: 2.5 h · Objetivo: diseñar, implementar y probar tools propias que el agente pueda invocar.

Objetivos de aprendizaje

  • Explicar qué es una tool y cómo el agente la descubre.
  • Crear skills del workspace (SKILL.md) con frontmatter y gating.
  • Construir tools combinando exec, apply_patch, web_fetch y scripts propios.
  • Seguir buenas prácticas de seguridad y calidad.
  • Probar con openclaw agent --message y publicar en ClawHub.

2.1 ¿Qué es una tool y cómo la invoca el agente?

Una tool es una capacidad que el agente puede usar. El modelo no ejecuta código directamente: pide usar una tool, y OpenClaw la ejecuta y le devuelve el resultado.

💡 Analogía: el agente es un empleado con un cajón de herramientas. No sabe soldar, pero sabe cuándo pedir el soldador.

El ciclo de una tool:

  1. El modelo ve la lista de tools disponibles.
  2. Decide que necesita una y la invoca con argumentos.
  3. OpenClaw ejecuta la tool.
  4. El resultado vuelve al modelo, que lo usa para responder.

2.2 Skills del workspace: el SKILL.md

Una skill es la forma principal de añadir capacidades al agente: una carpeta con un SKILL.md.

skills/
└── mi-skill/
    └── SKILL.md

Estructura de SKILL.md

---
name: mi-skill
description: Crea informes semanales en Markdown con métricas.
---

# Mi skill

Cuando el usuario pida un informe semanal:
1. Lee los datos de `data/`.
2. Genera un resumen con métricas.
3. Guárdalo en `informes/YYYY-MM-DD.md`.
CampoObligatorioQué hace
name✅Slug en minúsculas, dígitos y guiones. Debe coincidir con la carpeta.
description✅Una línea (<160 caracteres) para saber cuándo aplica.
user-invocableNoSi el usuario puede lanzarlo con /skill. Por defecto true.
disable-model-invocationNoSi true, el agente NO lo auto-invoca (solo /skill).
command-dispatchNoEnruta el comando directamente a una tool, sin pasar por el modelo.

Gating: que la skill solo cargue si hay requisitos

---
name: gemini-search
description: Busca en la web usando Gemini CLI.
metadata:
  openclaw:
    requires:
      bins: ["gemini"]        # necesita el binario 'gemini' en PATH
      env: ["GEMINI_API_KEY"] # necesita esa variable de entorno
---

Referencias con {baseDir}

Ejecuta el script de ayuda en `{baseDir}/scripts/run.sh`.

2.3 Construir tools: exec, apply_patch, web_fetch

exec — ejecutar comandos

# Skill: backup
Cuando el usuario pida hacer un backup:
1. Ejecuta: `tar -czf backups/temario-$(date +%F).tar.gz cursos/`
2. Confirma el archivo creado con `ls -la backups/`

apply_patch — editar varios archivos de forma estructurada

*** Begin Patch
*** Add File: cursos/mi-curso/02-tools.md
+# Tools personalizadas
+Contenido del módulo 2...
*** Update File: cursos/mi-curso/temario.md
@@
-| 2 | Herramientas | 1 semana |
+| 2 | Herramientas | 2 semanas |
*** End Patch
💡 apply_patch por defecto solo escribe dentro del workspace (workspaceOnly: true). Protección por defecto.

web_fetch — traer contenido de una URL

# Skill: resumir-doc
Cuando el usuario pida resumir una URL:
1. Haz `web_fetch` de la URL.
2. Resume los puntos clave en 5 bullets.

2.4 Buenas prácticas: seguridad y calidad

  1. Prompts concisos: la skill instruye qué hacer.
  2. Control de comandos: valida/sanitiza argumentos si usas exec.
  3. Menos privilegios: la skill solo usa las tools necesarias.
  4. Un archivo por módulo: más fácil revisar y reutilizar.
  5. Prueba antes de publicar: openclaw agent --message "...".

2.5 Probando tus tools

# Desde la terminal
openclaw agent --message "crea el temario de un curso de Python"

# O verifica que la skill cargó
openclaw skills list
⚠️ Gotcha: el agente solo "ve" las skills cargadas al inicio de su sesión. Cambios a mitad de sesión requieren /new o reinicio (openclaw gateway restart).

2.6 Publicar en ClawHub

npm i -g clawhub
clawhub login
clawhub skill publish ./skills/mi-skill
💡 Antes de construir desde cero, busca en clawhub.ai — quizá ya existe la skill que necesitas. Reutilizar > reinventar.

Errores comunes

  1. name con mayúsculas o espacios: no se carga. Usa minúsculas + guiones.
  2. description muy larga: una línea <160 caracteres.
  3. Carpeta y name distintos: deben coincidir.
  4. Skill no visible tras crearla: falta /new o reiniciar.
  5. Inyección de comandos: nunca interpoles input no confiable en exec.

Ejercicios

  • ☐ Crea una skill resumir-url que use web_fetch.
  • ☐ Crea una skill backup-temario que use exec.
  • ☐ Prueba ambas con openclaw agent --message "...".
  • ☐ (Opcional) Publica una en ClawHub.

Resumen

  • Las tools son el cajón de herramientas; el modelo decide cuándo usarlas según sus descripciones.
  • Una skill = carpeta + SKILL.md.
  • El gating hace que las skills solo carguen si hay requisitos.
  • exec, apply_patch y web_fetch son los ladrillos.
  • Prueba siempre y reinicia//new tras crear skills.
  • ClawHub para compartir y reutilizar.

Módulo 3: Agentes múltiples y rutas de sesión

Duración: 2.0 h · Objetivo: configurar varios agentes con workspaces y sesiones aisladas, y enrutar tráfico entre ellos.

Objetivos de aprendizaje

  • Configurar múltiples agentes con workspaces aislados.
  • Entender la diferencia entre sesiones main, aisladas y persistentes.
  • Delegar tareas a subagentes (sessions_spawn, sessions_send).
  • Enrutar canales y remitentes a agentes concretos.
  • Coordinar agentes en flujos reales.

3.1 Multi-agente: cada empleado, su propio escritorio

{
  agents: {
    defaults: {
      workspace: "~/.openclaw/workspace",
    },
    list: [
      { id: "soporte", workspace: "~/.openclaw/workspace-soporte" },
      { id: "editor",  workspace: "~/.openclaw/workspace-editor" },
    ],
  },
}

¿Por qué separar agentes?

  • Diferentes dominios (soporte vs. edición).
  • Diferentes niveles de permisos o modelos.
  • Evitar que un flujo grande contamine el contexto de otro.
⚠️ El workspace por defecto (~/.openclaw/workspace) es compartido si no defines workspace por agente.

3.2 Sesiones: main, aisladas y persistentes

TipoQué esCuándo usarlo
MainSesión principal del agente (DMs)Conversaciones normales contigo
AisladaContexto fresco, sin historial previoTareas puntuales que no contaminan
PersistenteSesión nombrada que acumula historialFlujos que construyen sobre resúmenes previos
Por canal/grupoCada grupo tiene su sesiónSeparar contextos por grupo
💡 Analogía: la sesión main es tu escritorio; una aislada es un cuarto desechable; una persistente es un proyecto en curso.

3.3 Subagentes y delegación

sessions_spawn(
  task: "Investiga y resume la doc oficial sobre MCP en OpenClaw.
         Devuelve un resumen de 10 líneas con los pasos de configuración.",
  taskName: "investigador-mcp",
  mode: "run" // one-shot: corre y termina
)
sessions_send(
  sessionKey: "<sesión destino>",
  message: "¿Terminaste el resumen de MCP?"
)

Cuándo delegar: lectura masiva de archivos, búsquedas web múltiples, tareas que generan mucho texto intermedio.

Cuándo NO delegar: consultas rápidas o de una sola lectura.

3.4 Enrutamiento por canal y por remitente

{
  channels: {
    telegram: {
      allowFrom: ["+15555550123"],
      agents: { "*": "soporte" },  // todo Telegram → 'soporte'
    },
    slack: {
      agents: { "*": "editor" },    // todo Slack → 'editor'
    },
  },
}
{
  messages: {
    groupChat: { mentionPatterns: ["@soporte", "@openclaw"] },
  },
}

3.5 Coordinación entre agentes: casos reales

  • Pipeline de contenido: investigador → editor → revisor.
  • Soporte escalado: soporte en Telegram, dev en Slack, aislamiento total.
  • Reportero automático: cron recolecta métricas → editor formatea → se publica.
💡 La clave de la coordinación: tareas claras y entregables explícitos en cada sessions_spawn/sessions_send.

Errores comunes

  1. No definir workspace por agente: colisión de contexto.
  2. Delegar todo a subagentes: sobrecarga.
  3. No esperar resultados: olvidar sessions_yield.
  4. Enrutamiento ambiguo: sin allowlist cualquiera habla con tu agente.
  5. Contexto contaminado: usar sesión main para trabajos masivos.

Ejercicios

  • ☐ Crea un segundo agente con su propio workspace.
  • ☐ Lanza un subagente con sessions_spawn y recolecta el resultado.
  • ☐ Enruta un canal concreto a tu segundo agente.
  • ☐ Configura mentionPatterns para un grupo.

Resumen

  • Multi-agente = varios empleados, cada uno con su escritorio y memoria aislada.
  • Sesiones: main, aisladas (desechables), persistentes (proyecto).
  • Subagentes (sessions_spawn) delegan; sessions_send comunica.
  • Enrutamiento por canal/remitente decide qué agente responde dónde.
  • Coordina con objetivos y entregables explícitos.

Módulo 4: Automatización avanzada con cron

Duración: 2.0 h · Objetivo: programar jobs recurrentes y puntuales con entrega a canales o webhooks.

Objetivos de aprendizaje

  • Crear jobs con los 4 tipos de schedule.
  • Elegir el payload correcto (system event, agent message, command).
  • Enrutar jobs a la sesión adecuada.
  • Entregar resultados por announce, webhook o none.
  • Gestionar jobs y entender reintentos/fallos.

4.1 El scheduler: el encargado de las alarmas

⚠️ Cron corre dentro del proceso del Gateway. Si el Gateway está apagado, los jobs no disparan. Persisten en la base SQLite del estado.

Tipos de schedule

TipoFlagEjemploUso
Puntual--at--at "20m"Recordatorio de una sola vez
Intervalo--every--every 1dCada X tiempo fijo
Expresión cron--cron--cron "0 9 * * 1"Reglas complejas (5-6 campos)
Al salir--on-exit—Cuando un comando termina
⚠️ Zonas horarias: sin --tz, cron usa la zona del host. Un --at sin zona se trata como UTC. Usa --tz America/New_York.

Ejemplo de expresión (5 campos): minuto hora día-mes mes día-semana

  • 0 9 * * 1 → todos los lunes a las 9:00.
  • */15 * * * * → cada 15 minutos.
💡 Gotcha clásico: día-de-mes + día-de-semana se interpreta con lógica OR. Para AND usa el modificador +1 de croner (ej. 0 9 15 * +1).

4.2 Tipos de payload

PayloadFlagQué haceCuándo
System event--system-eventInyecta texto, sin llamar al modeloRecordatorios simples
Agent message--messageTurno de agente con modeloRevisiones, análisis
Command--commandScript en el host, sin modeloTareas deterministas
 
openclaw cron add \
  --name "Revisar temario" \
  --at "2027-02-01T16:00:00Z" \
  --session main \
  --system-event "Recordatorio: revisa `cursos/mi-curso/temario.md`." \
  --wake now \
  --delete-after-run

4.3 Sesiones objetivo

ValorCorre enUso típico
mainCarril de wake de la sesión principalRecordatorios / system events
isolatedSesión aislada cron:<jobId>Reportes, tareas que no contaminan
currentSesión actualTrabajo recurrente con contexto
session:<id>Sesión persistenteFlujos que acumulan contexto

4.4 Entrega: announce, webhook y none

ModoQué hace
announceEntrega el texto final al canal objetivo
webhookPOST del evento terminado a una URL
noneSin entrega automática
 
openclaw cron create "0 9 * * 1" \
  "Revisa `cursos/mi-curso/temario.md` y avísame si hay inconsistencias o mejoras." \
  --name "Revisión semanal del temario" \
  --tz "America/New_York" \
  --session isolated \
  --announce \
  --channel slack \
  --to "channel:C1234567890"
openclaw cron create "0 18 * * 1-5" \
  "Resume los cambios del día en JSON." \
  --name "Digest diario" \
  --webhook "https://mi-app.com/openclaw/cron"
⚠️ Idioma: los jobs de cron no infieren idioma. Si quieres español, díselo en el prompt.

4.5 Gestión

openclaw cron list              # listar jobs
openclaw cron get <jobId>       # ver un job como JSON
openclaw cron show <jobId>      # ver job + ruta de entrega
openclaw cron enable/disable <jobId>
openclaw cron run <jobId>       # forzar ejecución
openclaw cron run <jobId> --wait
openclaw cron runs --id <jobId> # historial
openclaw cron remove <jobId>    # borrar

Reintentos y fallos:

  • One-shot: errores transitorios reintentan hasta retry.maxAttempts (default 3). Un error permanente desactiva el job.
  • Recurrente: backoff (30s, 60s, 5m, 15m, 60m). Se resetea tras un éxito.
  • Alertas: --failure-alert-after <n>.

Errores comunes

  1. Zona horaria equivocada.
  2. Gateway apagado: los jobs no disparan.
  3. --session main con --message: usa isolated/current.
  4. Sin idioma en el prompt.
  5. Día-mes + día-semana con OR.
  6. Job aislado sin contexto: no hereda tu conversación.

Ejercicios

  • ☐ Crea un recordatorio puntual con --at "5m", --session main, --system-event, --delete-after-run.
  • ☐ Programa una revisión aislada recurrente que anuncie por tu canal.
  • ☐ Envía un resumen a un webhook (https://webhook.site).
  • ☐ Ejecuta openclaw cron list y runs --id.

Resumen

  • Cron es el programador interno del gateway; los jobs persisten en SQLite.
  • Schedules: at, every, cron, on-exit — con --tz.
  • Payloads: system event, agent message, command.
  • Sesiones: main, isolated, current, session:<id>.
  • Entrega: announce, webhook, none.

Módulo 5: Integración con Model Context Protocol (MCP)

Duración: 2.0 h · Objetivo: conectar servidores MCP y exponer sus herramientas al agente.

Objetivos de aprendizaje

  • Explicar qué es MCP y cómo encaja en la arquitectura.
  • Configurar servidores MCP (local/stdio, HTTP, remotos).
  • Exponer tools de MCP al agente y a jobs de cron.
  • Aplicar seguridad y permisos a las tools MCP.
  • Conectar ejemplos reales: BD, APIs, navegador.

5.1 ¿Qué es MCP?

MCP (Model Context Protocol) es un estándar abierto para conectar herramientas y servicios externos a un agente de IA de forma uniforme.

💡 Analogía: si las tools nativas son el cajón, MCP es el contrato de enchufes que permite conectar aparatos de cualquier fabricante.
[Agente OpenClaw] ←→ [Cliente MCP] ←→ [Servidor MCP] ←→ [Servicio externo]
                                                       (BD, API, navegador…)
  • Cliente MCP: lo incorpora OpenClaw.
  • Servidor MCP: expone herramientas/recursos de un servicio.
  • Transportes: stdio (proceso local), HTTP/SSE (remoto).

5.2 Configurar servidores MCP

Servidor local (stdio)

{
  mcp: {
    servers: {
      "mi-base-datos": {
        command: "npx",
        args: ["-y", "@modelcontextprotocol/server-sqlite"],
        env: {
          SQLITE_PATH: "/data/app.db",
        },
      },
    },
  },
}

Servidor remoto (HTTP)

{
  mcp: {
    servers: {
      "api-externa": {
        url: "https://api.ejemplo.com/mcp",
        // auth según el servidor
      },
    },
  },
}

5.3 Exponer tools de MCP al agente y a cron

openclaw cron create "0 7 * * *" \
  "Consulta la BD y envía el resumen de actividad diaria." \
  --name "Reporte diario BD" \
  --session isolated \
  --announce \
  --channel telegram \
  --to "-1001234567890"

5.4 Seguridad y permisos

  • Allowlists de tools: restringe qué tools MCP puede usar.
  • Permisos por agente: menos privilegios.
  • Auth segura: tokens con el menor alcance.
  • Revisa el servidor: solo fuentes confiables.
{
  agents: {
    defaults: {
      toolsAllow: ["mcp.mi-base-datos.consulta", "mcp.mi-base-datos.inserción"],
    },
  },
}
💡 Analogía de seguridad: darle al empleado una tarjeta de acceso restringido: puede entrar a la sala que necesita, no a todo el edificio.

5.5 Ejemplos prácticos

  • Base de datos (SQLite): consultar tablas, crear/leer registros.
  • API externa: "¿Qué tiempo hará mañana en Madrid?"
  • Navegador: automatizar páginas web.
💡 Consejo: busca servidores MCP existentes en los registros de la comunidad antes de construir uno.

Errores comunes

  1. Servidor MCP no arranca: revisa command, args, env.
  2. Remoto sin auth: los servidores HTTP suelen requerir token/OAuth.
  3. Exponer TODO el servidor: menos privilegios.
  4. MCP de fuente no confiable: vector de ataque.
  5. Confundir MCP con tools nativas.

Ejercicios

  • ☐ Conecta un servidor MCP local (ej. SQLite) y pide una consulta.
  • ☐ Conecta un MCP remoto con autenticación.
  • ☐ Restringe el alcance con toolsAllow.
  • ☐ Programa un job de cron que use una tool MCP.

Resumen

  • MCP estandariza el uso de servicios externos (el "enchufe universal").
  • Configura servidores locales (stdio) o remotos (HTTP).
  • Las tools MCP quedan disponibles para el agente y para cron.
  • Seguridad: allowlists, menos privilegios, auth mínima.

Módulo 6: RAG, embeddings y bases de datos vectoriales

Duración: 2.5 h · Objetivo: montar un pipeline RAG: indexar documentos, generar embeddings y recuperar contexto.

Objetivos de aprendizaje

  • Explicar RAG, embeddings, similitud vectorial y chunking.
  • Usar la memoria y búsqueda semántica de OpenClaw.
  • Elegir y configurar una base vectorial.
  • Configurar proveedores de embeddings y memorySearch.
  • Integrar RAG en un agente.

6.1 Conceptos: el archivador inteligente

💡 Analogía: un empleado con RAG tiene un archivador inteligente: ante una pregunta, busca los papeles más relevantes y los lee antes de contestar.

Piezas clave:

  • Embedding: un vector de números que representa el significado de un texto.
  • Similitud vectorial: cómo de "cerca" están dos vectores (coseno, euclidiana…).
  • Chunking: dividir documentos grandes en fragmentos.
  • Base vectorial: almacén optimizado para buscar por similitud.
1. INDEXADO:
   Documentos → chunking → embeddings → base vectorial

2. CONSULTA:
   Pregunta → embedding de la pregunta
   → buscar chunks más similares (top-k)
   → inyectar chunks en el prompt → el modelo responde con contexto

6.2 Memoria y búsqueda semántica en OpenClaw

  • memory_search — encuentra notas por significado (híbrido: vectores + keywords).
  • memory_get — lee un archivo o rango de líneas.
openclaw memory status          # estado del índice
openclaw memory search "MCP config"   # búsqueda semántica
openclaw memory index --force   # reconstruir el índice

6.3 Bases de datos vectoriales

BaseCuándo usarla
SQLite (builtin)Default; sin dependencias extra. Perfecta para empezar.
QMDSidecar local con reranking. Búsquedas más precisas, todo local.
LanceDBPlugin con embeddings OpenAI-compatibles y Ollama local.
QdrantBase dedicada, escalable, en contenedor. Ideal producción.
pgvectorExtensión de PostgreSQL. Si ya usas Postgres.
💡 Regla práctica: aprende con SQLite builtin; en producción pasa a Qdrant o pgvector.

6.4 Proveedores de embeddings y memorySearch

{
  agents: {
    defaults: {
      memorySearch: {
        provider: "ollama", // o: openai, gemini, voyage, mistral, bedrock, local GGUF, LM Studio…
      },
    },
  },
}
💡 Tip local/privado: para no enviar documentos a la nube, usa Ollama o LM Studio con embeddings locales.

6.5 Integrar RAG: caso práctico

  1. Configura el proveedor de embeddings.
  2. Indexa tu corpus: openclaw memory index --force.
  3. Pregunta con contexto: el agente usa memory_search.
  4. (Producción) Base externa: conecta Qdrant/pgvector vía MCP (une Módulo 5 y 6).

Errores comunes

  1. Chunking mal dimensionado.
  2. Embeddings sin contexto: corpus ruidoso = búsqueda ruidosa.
  3. No reindexar tras cambiar documentos.
  4. Proveedor no configurado: sin embeddings solo hay keyword.
  5. RAG sin citas: debe decirte de dónde sacó la info.

Ejercicios

  • ☐ Configura un proveedor y reconstruye el índice.
  • ☐ Indexa 3-5 documentos y haz búsquedas semánticas variando palabras.
  • ☐ Levanta Qdrant en Docker y conecta un MCP de vectores.
  • ☐ Pide una respuesta que combine RAG + conocimiento y evalúa la calidad.

Resumen

  • RAG = dar contexto al modelo antes de responder.
  • Embeddings = vectores que representan significado.
  • Chunking = partir documentos en fragmentos.
  • memory_search/memory_get con búsqueda semántica híbrida.
  • Bases: SQLite builtin → Qdrant/pgvector.
  • Reindexa cuando cambies los documentos.

Módulo 7: Despliegue en contenedores Docker

Duración: 2.0 h · Objetivo: contenerizar el gateway OpenClaw y sus servicios complementarios.

Objetivos de aprendizaje

  • Escribir un Dockerfile que levante el gateway.
  • Orquestar un stack con Docker Compose.
  • Persistir estado con volúmenes.
  • Gestionar redes, puertos y variables de entorno.
  • Aplicar buenas prácticas (sin secretos, healthchecks, logs).

7.1 ¿Por qué Docker? La mudanza perfecta

💡 Analogía: Docker es la caja de mudanza con etiqueta. Empaquetas el edificio, lo etiquetas y lo llevas a cualquier host.

Beneficios:

  • Reproducibilidad: misma imagen → mismo comportamiento.
  • Aislamiento: no ensucia el host.
  • Orquestación: Compose levanta gateway + Qdrant + MCP juntos.
  • Persistencia controlada: volúmenes deciden qué sobrevive.

7.2 El Dockerfile del gateway

# 1. Base: imagen oficial de Node
FROM node:24-slim

# 2. Instala OpenClaw globalmente
RUN npm install -g openclaw@latest

# 3. Directorio del workspace
WORKDIR /workspace

# 4. Copia tu config (sin secrets: usa variables de entorno)
COPY openclaw.json /root/.openclaw/openclaw.json

# 5. Expón el puerto del gateway (Control UI)
EXPOSE 18789

# 6. Comando de arranque
CMD ["openclaw", "gateway", "start"]
⚠️ Nunca copies API keys en la imagen. Se pasan por variables de entorno.

7.3 Docker Compose: el stack completo

services:
  gateway:
    build: .
    container_name: openclaw-gateway
    ports:
      - "18789:18789"
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY} # del .env
      - TZ=Europe/Madrid
    volumes:
      - ./workspace:/workspace
      - openclaw_state:/root/.openclaw
    restart: unless-stopped

  qdrant:
    image: qdrant/qdrant
    container_name: openclaw-qdrant
    ports:
      - "6333:6333"
    volumes:
      - qdrant_data:/qdrant/storage
    restart: unless-stopped

volumes:
  openclaw_state:
  qdrant_data:

7.4 Redes, puertos y variables de entorno

# .env (NO versionar)
OPENAI_API_KEY=sk-...
⚠️ Añade .env a tu .gitignore.
  • 18789 → Gateway / Control UI.
  • 6333 → Qdrant REST.

7.5 Buenas prácticas

  1. Sin secretos en la imagen.
  2. Volúmenes para todo lo que deba persistir.
  3. Healthcheck.
  4. Logs a stdout (Compose los captura).
  5. restart: unless-stopped.
  6. Versión fija de la imagen.
  7. .gitignore para .env y datos de volumen.

Errores comunes

  1. API key en la imagen.
  2. Sin volumen en el workspace: pierdes trabajo al recrear.
  3. Confundir down con reinicio: los volúmenes nombrados persisten (salvo -v).
  4. Zona horaria por defecto (UTC).
  5. Exponer puertos innecesarios.
  6. Sin healthcheck.

Ejercicios

  • ☐ Escribe un Dockerfile.
  • ☐ Crea un docker-compose.yml con gateway + Qdrant.
  • ☐ Levanta el stack y verifica que responde en 18789.
  • ☐ Detén y recrea; comprueba que persiste.
  • ☐ Añade un healthcheck y revisa logs.

Resumen

  • Docker = empaquetado reproducible.
  • Dockerfile: base Node, instala OpenClaw, expone 18789.
  • Compose orquesta gateway + servicios.
  • Persistencia: volúmenes.
  • Seguridad: API keys por env vars, healthchecks.
